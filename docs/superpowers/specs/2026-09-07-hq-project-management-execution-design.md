# HQ 프로젝트 관리 및 실제 작업 실행 설계 초안

상태: 사용자가 “모두 진행해줘”로 승인. 기존 조회 전용 서비스는 실행 중이며 이 설계의 기능은 아직 구현되지 않았다.

## 목표
Slack, Telegram, 로컬 터미널에서 동일한 프로젝트 관리와 실제 개발 작업을 수행한다. 로그인된 Codex 구독 인증을 사용하며 OpenAI API 키를 요구하지 않는다. 음성은 이번 범위에서 제외한다.

## 접근 방식 비교
1. 권장: 기존 실행 서비스와 Orca 작업자 기능에 세 입력 경로를 연결한다. 작업 상태·중복 방지·작업 공간 관리 기능을 재사용하되 실제 연결부 검증이 필요하다.
2. 조회 런타임에서 Codex shell 실행만 추가한다. 초기 연결은 작지만 기존 작업 생명주기와 이중화되어 중지·재시도·복구 일관성이 깨질 수 있다.
3. 채널마다 독립적인 실행기를 만든다. 개별 구현은 가능하지만 프로젝트와 작업 상태가 분산된다.

## 프로젝트 관리
- Orca를 프로젝트 ID와 실제 경로의 기준으로 사용한다. 목록과 작업 시작 시 Orca 등록 프로젝트를 동기화하고 정확히 5개 제한을 제거한다.
- Orca에 등록된 프로젝트는 별도 HQ 설정 파일 편집 없이 이름 또는 ID로 지정할 수 있다. 같은 이름이 여러 개면 대상만 확인한다.
- 세 입력 경로에서 목록, 동기화, 프로젝트 등록, 별칭 설정, HQ 사용 제외/복원을 지원한다.
- 로컬 경로 등록은 해당 Mac의 실제 저장소를 확인한 뒤 Orca 공식 등록 기능을 통해 수행한다. 실제 CLI 지원 계약은 구현 계획 전에 확인한다.
- HQ 사용 제외는 저장소 파일 삭제나 Orca 등록 해제를 의미하지 않는다. 명령 응답에 효과를 명시한다.
- 실행 중인 프로젝트의 경로 변경/제외는 진행 중 작업을 훼손하지 않도록 거부하고 해당 작업 ID를 안내한다.
- 기존 프로젝트별 민감 경로와 보호 규칙은 동기화 시 보존한다.

## 통합 명령과 작업 흐름
- Slack 비공개 채널, 지정 Telegram 개인 대화, 로컬 hq CLI가 하나의 명령 서비스와 영속 작업 기록을 사용한다.
- Slack 사용자 ID, Telegram 사용자 ID, 로컬 사용자 신원을 동일 소유자로 연결한다. 봇/다른 사용자의 메시지는 실행 명령으로 취급하지 않는다.
- 자연어 요청을 프로젝트 관리, 조회, 개발 작업, 작업 제어로 구분한다. 구조화된 CLI 명령도 같은 서비스로 들어온다.
- 실제 개발 작업은 코드 조사, 수정, 테스트, 빌드, 결과 보고를 지원한다. 기본 실행자는 기존 로그인 인증을 사용하는 Codex다.
- 작업별 Orca 작업 공간과 브랜치를 사용하고, 기존 실행 서비스의 편집 잠금·작업자 식별·검증 흐름을 재사용한다.
- 접수 시 작업 ID, 대상 프로젝트, 실행 위치를 알린다. 진행 상황과 변경 파일·검증 결과·실패 원인을 원래 대화에 전달한다.
- 세 입력 경로에서 작업 목록, 상태, 후속 지시, 중지, 재시도를 지원한다. 다른 채널에서도 같은 작업 ID로 접근한다.
- 일반적인 코드 수정과 테스트는 명시적인 작업 지시로 실행한다. 커밋·푸시·PR·배포는 해당 요청의 명시된 범위에 따라 처리하고, 불명확한 대상/파괴적인 조작만 확인한다.
- 후속 지시는 해당 작업 문맥에 연결한다. 이미 실행 중인 작업은 기존 요청을 임의로 교체하지 않고 큐에 기록한다.

## 데이터와 복구
- 프로젝트 설정 갱신은 원자적으로 저장하고 변경 주체를 기록한다.
- 메시지 중복 수신은 동일 작업을 다시 실행하지 않는다. 응답 전송 재시도와 개발 작업 재시도를 분리한다.
- 재시작 시 실행 중 작업을 Orca의 실제 작업자 상태와 대조한다. 상태 불명 시 자동 재실행하지 않고 복구 필요 상태로 보고한다.
- CLI는 실행 중 gateway의 로컬 인증된 경로로 연결하며 별도 작업 큐를 만들지 않는다. 인증정보나 개발 명령을 Tailscale 상태 페이지에 노출하지 않는다.
- 한 채널 장애가 다른 채널의 작업 접수를 막지 않도록 readiness와 채널별 상태를 구분한다.

## 보호 사항
- 기존 사용자 변경사항을 보존한다. 기존 보호 roadmap 파일은 읽기·수정·hash·diff·stage·restore 대상에서 제외한다.
- 보호 파일을 대상으로 하는 작업은 거부하고 이유를 안내한다. 프로젝트 자동 등록으로 이 규칙이 사라지지 않는다.
- 자격증명은 Keychain 및 사용자 직접 입력 흐름을 유지한다.

## 구현 순서와 수용 기준
1. 프로젝트 동기화/관리와 공통 명령 서비스, CLI 연결. 5개 초과·중복 이름·제외·잘못된 경로·보호 설정 보존을 검증한다.
2. 기존 실행 서비스 및 Codex 작업자 실제 연결. 작업 공간 생성부터 수정·테스트·상태·중지·재시도·재시작 복구를 검증한다.
3. Slack/Telegram 연결과 채널 간 작업 제어. 각 입력 경로에서 프로젝트 관리와 작은 개발 작업이 끝까지 수행되어야 한다.
4. 설치본 반영 및 doctor/status/health 갱신. 실제 사용자 요청으로 파일 변경, 테스트 결과, 사용자 응답 수신까지 검증한 뒤 완료 보고한다.

최종 보고는 구현된 명령, 실제 검증 결과, 미지원 범위, 설치 상태, 커밋·푸시 여부를 포함한다. 기존 조회 전용 E2E와 Tailscale Serve 검증도 미완료 항목으로 유지하며 새 기능의 완료 근거로 대체하지 않는다.

## 사용자 아키텍처 정정 — 기존 실행 설계보다 우선
HQ는 Orca 오케스트레이션의 중간 채널이다. HQ 자체 Codex 실행기, sandbox, 작업 스케줄러, 독립 작업 생명주기를 설치하지 않는다. Orca Run/Task/Dispatch/Worker가 실제 상태의 기준이며 HQ는 신원 확인, 채널 입력 전달, native ID 연결, 관찰한 상태 알림 재전송만 담당한다. Orca에서 직접 시작한 작업도 native 조회/후속 지시 경로를 사용한다. 실제 task 등록과 worker 시작은 공식 Orca orchestration 명령을 사용한다. 비오케스트레이션 직접 터미널 작업은 해당 상태로 표시하고 완료율을 지어내지 않는다. 기존 custom 실행 smoke는 폐기된 접근의 증거이며 새 native 완료 근거로 사용하지 않는다.
